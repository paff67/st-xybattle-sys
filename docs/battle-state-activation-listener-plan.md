# 战斗状态进入“待裁定”的独立监听器方案

日期：2026-10-09。状态：独立监听器已实现，默认关闭；本地回归、语法检查与构建已通过，真实宿主完整验收待完成。实现与验证范围见 [开发记录](battle-state-activation-listener-development.md)。以下保留原实施方案及验收要求。

## 目标与范围

当当前聊天、当前有效消息分支的 `世界.战界.战斗状态` 从一个有效的其他值变为 `待裁定` 时，自动唤起已有战斗模块，复用参战人物提取、战斗准备及后续裁定流程。

监听器只读 MVU，不向 MVU/ACU 写入任何内容。四字段保持原样，不增加人员表、事务字段或设施数据。监听记录保存在扩展自己的 `xy_event_v1` 元数据中。

“唤起”指提交一次有身份的战斗准备请求，不等于已经开始一次攻防，更不等于已经产生成败。不能把打开窗口当成接管完成，也不能把触发状态当作玩家选择了某招式。

## 已确认的代码基础与缺口

| 已有基础 | 本次需要补充 |
| --- | --- |
| `event-battlefield-state.js` 校验四字段 | 纯状态转移检测，保留未知/缺失与“无”的区别 |
| P1 已保存消息 UID、swipe UID、分支身份、正文请求绑定 | 为正文后的变量观察提供稳定、只读的身份查询，覆盖已绑定的当前尾部助手消息 |
| `HostEventStore` 保存扩展元数据并回读 | 增加兼容旧存档的监听记录，不能与现有协调器分别覆盖旧 revision |
| `EventOperationLock` 与战斗提交共享锁 | 战斗准备入口也进入同一串行调度；现有锁没有自动排队功能 |
| `event-runtime.js` 有语义转交和正文后观察入口 | 三种来源统一经过一次 battle-entry broker，再交给控制器 |
| `App.vue` 的 `onBattleEntry` 打开工作台并调用准备 | 将业务接管移出 UI 回调，返回结构化结果；UI 只负责展示 |
| `prepareCharacters()` 支持传入 context/MVU 适配 | 从触发消息显式读取快照，不借用默认“最新消息” |

本地保存的 `@types/iframe/exported.mvu.d.ts` 中，`VARIABLE_UPDATE_ENDED` 提供 `(variables, variables_before_update)`，`BEFORE_MESSAGE_UPDATE` 提供 `{variables, message_content}`。两者均未声明消息 ID；后者还是写入前通知。因此这份类型定义只能作为适配依据，部署前须在 yiyu 核实实际事件总线、参数、数据写入时序及 iframe 可见范围。

旧 `host-contract-review.md` 中涉及扩展直接写变量的建议不适用于本功能，以当前用户明确的“扩展不负责 MVU/ACU 写回”为准。

## 触发规则

```js
const edge = validBefore && validAfter
  && before.战斗状态 !== '待裁定'
  && after.战斗状态 === '待裁定';
```

这里只定义值的条件，实际发起还须满足消息已完成、变量落在该消息分支、身份仍有效、事件未处理、未取消、没有相冲突的活动战局等条件。

| 观察到的变化 | 行为 |
| --- | --- |
| 无 → 待裁定 | 新战斗准备候选 |
| 已结束 → 待裁定 | 新战斗准备候选；检查此前会话是否确已结束 |
| 进行中 → 待裁定 | 若已有同一战局则关联/恢复现有会话，不重建人物、不自动打一回合 |
| 待裁定 → 待裁定 | 不触发；即使其他字段改变也不以此启动另一战斗 |
| 备案状态变化、进入战界，但战斗状态不是待裁定 | 不触发 |
| 字段缺失/格式错误 → 待裁定 | 不当作可靠边沿；提示需要补齐有效基线，提供手动入口 |
| 初次打开聊天就看见待裁定 | 只建立基线，不回放历史战斗；可提示“已有待裁定状态，打开战斗准备” |
| 切换到旧 swipe 后看到待裁定 | 不把界面切换当作新世界事件 |
| 新生成的 swipe 在其实际父状态上出现有效边沿 | 按新分支独立判断，不能以离开的 swipe 作为 before |

允许现实空间、战界 ID 为无时的真实交锋候选；备案不是前提。下沉战界缺少 ID 属于四字段格式不完整，需要诊断而非编造编号。不同战界 ID 的活动战局不得自动合并；在现实中没有战界 ID 时，由消息因果关系和已关联的会话身份判断，不能把所有“无”都视为同一战斗。

## 观察和读取流程

1. **注册窗口**：在原生生成开始时建立待观察请求；收到精确 `MESSAGE_RECEIVED` 后关联助手消息。MVU 可能早于 P1 `finish()` 发出事件，因此先暂存信号，等正文绑定完成再处理。
2. **记录提示信号**：订阅 MVU 更新事件，只复制前后数据和必要摘要，不修改事件参数。不在回调内保存整个聊天或等待网络模型，以免阻塞 MVU 自身更新。
3. **关联目标**：优先使用宿主实际提供的消息/分支身份；若没有，使用已捕获请求、消息对象身份、当前 swipe、写入前通知的内容及目标消息数据变化共同关联。仅凭时间相近、相同正文或最新楼层不够。多个可能目标时不自动启动。
4. **等待数据落入该分支**：在正文完成、目标变量实际可读、已有变量分析结束后，对指定消息回读。`VARIABLE_UPDATE_ENDED` 只是重读信号，不是已保存证明；`BEFORE_MESSAGE_UPDATE` 也不能作为成功回执。
5. **确认变化来源**：同一消息再次更新时，以同一分支上一次已确认状态为 before；新助手消息以其生成前的当前分支有效状态为基线。不得用上一个打开的聊天或刚离开的 swipe 比较。
6. **队列提交**：满足边沿后创建候选，等待原生生成及 P0/P1 操作完成，取得共享锁，再次读取 scope、变量、分支、控制器状态与最新存档 revision。状态已离开待裁定或消息失效时丢弃。
7. **持久化与接管**：保存触发记录并确认回读后，调用统一战斗准备入口；控制器接受后绑定 sessionId 并保存确认结果。

候选观察窗口可有配置化超时，例如 30 秒用于宿主变量更新等待。超时仅记录 `mvu_not_ready`，以后收到该请求的可靠更新仍可重新核对；不能把超时解释为更新成功。消息数据多次相等只是稳定性检查，不独立证明消息身份或写入完成。

运行中只观察当前分支的有效尾部消息。新用户输入到来会使尚未开始的候选过期，不能把前一轮准备偷偷移到新输入上。历史编辑/重新处理变量默认只更新诊断基线，不自动开战；当前有效尾部消息的明确重新处理，在能够证明前后更新身份时可按新更新轮次判断。

MVU 接口缺失或事件无法可靠关联时显示“状态监听不可用”，保留已有手动/语义入口，不退化为扫描正文中“待裁定”的关键词。ACU 只作信息对照，不能用异步全局表更新代替 MVU 边沿。

## 与已有入口的关系

建议第一阶段采用 **兼容模式**：保留已经可用的输入语义分流，同时增加状态监听。三条路径全部经过统一接管入口：

```text
输入语义分流 ───┐
正文交战观察 ───┼─ 战斗接管协调器 → 现有控制器准备流程
MVU状态边沿 ────┘
```

通过触发源的父请求、生成绑定、消息分支和已关联战斗 session 合并同一次唤起。例如语义入口已经启动战斗，随后正文投影为待裁定，只关联现有 session，不再提取一遍人物。

这不是要求 AI 再决定“要不要接受待裁定”。边沿已经提供唤起意图，后续只校验作用域、所需数据、实际对手和当前会话；信息不足进入 `needs_context`，不能让模型编造一次战斗来满足状态。

若最终要求 **仅状态模式**，则关闭两条语义路径的“新建战斗唤起”，保留非战斗分流及已活动战斗的后续操作。该模式需要同步约束主 AI：首次正文只推进到即将交锋并输出待裁定，不能先写完成胜负再等待监听器。否则监听会晚于既成剧情，无法回头修正当前正文。首次实现不建议同时切换这一行为。

## 轻量的扩展元数据

建议在 `xy_event_v1` 下新增可选子对象 `battleActivation`，旧存档缺失时按空值读取。业务 MVU/ACU 不增加字段。

记录以下最小身份：

- 角色/聊天、branchUid、assistantMessageUid、swipeUid。
- 父 eventId/requestId、消息内容修订指纹、已确认变量更新轮次。
- 前后四字段摘要及资料快照指纹；不保存密钥或全套重复人物资料。
- activationId、来源集合、状态、原因、已关联 sessionId。

去重不能只用战界 ID，也不能只用四字段哈希。同一个消息中确有第二次 `进行中 → 待裁定` 需要可区分的更新轮次；重复同一个 MVU 回调不能凭回调次数创造新轮次。更新轮次由观察器确认的真实状态序列产生，并持久化。

建议生命周期：

```text
queued → preparing → accepted
                  → needs_context / failed / cancelled / obsolete
```

accepted 表示控制器已接受同一 activationId 并返回 sessionId，不等于已裁定出战果。资料不足时保留具体缺项和显式重试入口；自动流程不要求用户逐次批准，也不无限重试或编造资料。

新记录不能直接伪装成现有 `origin: native-user` 的 P1 输入事件。应通过独立记录引用其父 P1 事件；若以后扩展 event_v1 来源枚举，要同时更新校验、恢复及日志逻辑。

## 并发、保存与恢复

- 与现有 P0/P1、手动战斗共享 `EventOperationLock`；取得锁后重新 load 最新根对象，禁止用等待前的 root 覆盖新收据。
- 不在 MVU 解析过程中持锁调用全量 `saveChat()`。需要等宿主目标写入完成后再持久化扩展元数据，避免用旧消息状态覆盖刚写入的变量。
- 为准备阶段引入独立的短锁认领和可取消任务所有权；模型请求可在锁外运行，结果应用前重新取得锁并校验认领、scope 和快照。避免已有 `submit()` 再取同一非重入锁造成死锁。
- 控制器的 `requestBattleEntry({activationId, scope, ...})` 必须幂等：同一 ID 重试返回原接管结果，不新建 session。当前 UI 回调忽略参数且可能忙时直接返回，不能原封不动当作这个接口。
- `queued` 保存后崩溃：恢复时只处理仍有效且未过期的当前分支请求。`preparing` 保存但无结果：先查 session 是否已按该 ID 接受；能够确认才恢复，否则显示待恢复，不能盲目重复请求。`accepted` 恢复只重建 UI，不再次启动。
- 保存失败时区分“未提交”与“结果未知”，走现有保存回读/恢复机制。不能清空去重标记后直接重跑。
- Web Locks 只覆盖同源浏览器标签页；现有存储的回读校验不是跨设备原子 CAS。首版按同聊天单活动客户端验收，不承诺跨设备 exactly-once。

## 取消与用户体验

悬浮窗显示“检测到待裁定，正在准备战斗”以及具体阶段，如“读取当前人物”“提取对手资料”。沿用取消按钮和日志入口。

取消后立即废弃该 activationId 的后续结果，尽可能中止模型请求；保存取消消费记录。保留用户变量里的待裁定原值，不由扩展改成无或进行中。即使重复收到更新回调、刷新或切换界面，也不能重新自动唤起同一次候选。

新的、可证明的状态边沿可再次触发。若状态一直保持待裁定，用户可从工作台显式重试或开始，不必为了重试手改 MVU。取消标记绑定消息、分支和更新轮次，不永久屏蔽同一战界。

监听器通常在正文与 MVU 更新后启动，此时当前正文已经生成。取消只停止后续准备，不再补发一轮正文、不注入裁定场景包。若同一父 P1 请求已标记 `user_skipped_adjudication`，该请求随后出现的 MVU 待裁定边沿也应直接记为跳过，避免用户刚取消又被监听器拉回战斗。

如果准备阶段与下一次用户发送竞争，应先撤销未被控制器接受的候选，让这次用户输入正常走原有入口；已接管战斗则由现有战斗输入规则处理。停止主 AI 生成、切换聊天或分支、编辑/删除源消息、关闭自动入口、卸载扩展，都需要释放观察器和任务；迟到响应不得改动新上下文。

## 正文和变量更新边界

监听器在正文完成后才能确认 MVU 边沿，不能把新结果注入已经完成的同一轮请求。

默认只唤起准备，不额外自动发送空消息或自动生成一轮正文。后续用户采取战斗行动时复用已有裁定和场景包流程。若之后希望自动进行首轮交锋，需要单独定义已授权动作、原生生成关联与取消语义，不应夹带在本监听器内。

控制器是否接管以扩展的 accepted/sessionId 为准，不要求 MVU 先变为进行中。后续场景包或限定到对应请求的宿主提示可提供“已实际接管”的状态事实，供正文按既有更新规则投影；没有产生正文前 MVU 可暂时仍为待裁定。不得仅为了消除重复触发而直接写变量。

## 实施和验收顺序

1. yiyu 做最小只读探针，确认 MVU 事件、目标消息数据和保存时序；不运行战斗裁定。若无法可靠关联，先解决宿主适配，不用时间延迟猜测。
2. 实现纯状态观察器和持久化去重；模拟事件先只记日志，不唤起。
3. 接入统一控制器入口，验证与已有语义路径、手动入口互斥，保持旧战斗执行器行为。
4. 接进度/取消/恢复 UI，再构建及同步分发镜像。
5. yiyu 测试准备和转交次数，不重复测试整套战斗胜负算法；真实模型仅验证人物提取/准备与实际入口兼容性。

最低验收矩阵：三种有效边沿、重复回调、持续待裁定、单纯备案/入场、缺字段、初始化待裁定、异步变量延迟、早于正文绑定的 MVU 事件、两轮相同正文、重生成与 swipe、同消息多次更新、取消及迟到响应、父请求已取消、活动战局续用、不同战局冲突、锁忙、保存失败、保存后崩溃、刷新恢复、切聊天、重复挂载和卸载、多标签竞争。

通过标准：每个合格边沿最多一次有效接管；重复或过期信号零新增接管；取消后零后续裁定与场景包注入；变量写入 API 调用数为零；普通输入与非战斗执行流程不受影响。真实宿主证据与本地模拟测试分别记录。
