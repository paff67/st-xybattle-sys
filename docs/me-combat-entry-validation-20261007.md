# me 战斗入口修复与真实模型验证

范围：`https://me.paff-67.top/` 的 `batter--test`，本地 Chrome 9222。仅测试入口、候选资料与既有战斗流程兼容，不执行战斗回合。

## 现场根因

- 原现场自动事务开关关闭，`xy_event_v1` 无分流记录。工作台展示的是 2026-10-04 的旧存档：沧澜湖心、许妍／厉沧海和离线裁定记录，不是本次正文中的太平洋、许妍／顾澜。
- 本地缓存键只含聊天和数字楼层分支；控制器恢复缓存没有验证助手消息 UUID。同一聊天删除后重建同一楼层，旧人物和回合会被恢复，宿主随后拒绝 `Receipt/session scope mismatch` 写入。
- 宿主自动执行器直接调用战斗状态核心，未接工作台既有的“开始战斗 → AI 人物档案 → 确认”入口。
- 人物提取截取每条消息开头 4000 字符，可能被长思考段占满；MVU 的无姓名 `主角` 容器无法按姓名匹配。敌人补全携带无关的主角规则库；模型超时又被视作外部取消，没有进入自动重试。

## 修复行为

缓存按消息 UUID 隔离，只迁移身份确实相同的旧缓存，原缓存保留用于恢复。开始和提交战斗都检查已确认的人物档案。

宿主战斗分流保存 `handed_off` 后停止本轮原生生成，释放 P1 锁并移交既有工作台。场景创建输入先生成正文；只观察本次准确关联的完成消息，以语义和原文证据判断是否进入战前准备。停止、编辑、换聊天、切 swipe 或新生成取消迟到观察。

人物提取移除思考与 HTML 辅助内容，读取当前正文。AI 同时提取当前场景，确认后才写入战局。MVU 主角按容器角色读取，敌人按姓名档案匹配，不把主角资料套给敌人。

敌人没有 MVU/ACU 档案是正常情况：AI 应依据上下文与境界生成完整功法、招式、资源、行为战术、弱点和隐秘设定。缺少原文的细节由 AI 设计，用户只审核或修改结果。敌人请求不携带主角整套规则库；超时自动重试一次，显式取消不重试。未完成的敌人生成显示重试提示，不要求用户手填敌人设定。

## 已验证

- 刷新测试卡后恢复为当前消息的空闲战前状态，旧厉沧海与旧离线回合没有再次进入；当前消息保存确认成功。
- 使用现场真实模型 `gpt-6.1-sol`，从已有正文识别顾澜重水尖刺杀阵与许妍水弓应战，进入人物确认页。
- 原生发送“我抬起水弓，正面迎击顾澜的重水尖刺。”，真实分流保存 `handed_off`，保留该用户消息，没有生成额外助手正文，战斗记录仍为零。事件锁释放，没有直接裁定或扣资源。
- 第一轮完整人物测试得到正确的许妍／顾澜身份及太平洋场景，但主角资料不足、敌人生成超时；这轮不计作完整档案验收，随后修正敌人生成请求和重试。

- 修复后仅输入实际聊天上下文，真实模型自动识别顾澜，人物识别 HTTP 200，耗时 38.6 秒；完整敌人生成先后两次达到 400 秒超时。已验证自动重试有效，但这组尚未获得完整敌人档案，不计作生成成功。
- 最终本地回归 220/220 全量通过，包含跨聊天迟到移交、敌人生成契约和超时重试检查；语法检查与发布构建通过。

- 同模型精简输出对照成功：在完整结构不变的前提下生成3个招式，输出上限4000，`createHttpCharacterInference.completeCandidate` 通过完整性校验并返回金丹初期顾澜。生成《鲸波暗潮诀》、重水刺阵、鲸波压潮、双梭踏流，以及0–100重水真元、消耗恢复规则、行为战术、弱点；未提供敌人的预置功法或资源资料。完整结果保存在本地 `output/me-gulan-generated-profile.json`。默认敌人策略据此采用精简完整定义与4000输出上限，不改变主角输出上限。

## 数据边界与回退

当前测试 MVU 主角仍是初始化的“凡人（DC:0）”，功法为空，与本次金丹场景正文不一致；未修改 MVU、世界书或主角设定来制造通过结果。敌方生成不依赖该初始化主角数据。完整开战仍需主角资料也满足现有检查，不等于本轮已验证战斗裁定。
